# Contributing

`README.md` covers the requirements and first-time setup. `make help` lists every build, test, and check target.

## Workflow

Read `spec/components.md`, then the spec for the area you work on. The specs describe what the product does, so a change in behavior updates the spec in the same commit. A new item under a spec's "Testable behaviors" needs a test that carries its identifier (for example, `TM-1`), which `make check-behaviors` enforces.

Build through the Makefile, not Xcode or a bare `xcodebuild`: it selects the right toolchain and generates `Config/Local.xcconfig` from your `local.mk`.

Logic belongs in `Packages/TimeTrackingCore`, where it can be tested without an app. The app targets hold views and platform glue.

## Before you commit

| Command | Checks |
|---|---|
| `swift test --package-path Packages/TimeTrackingCore` | Library tests |
| `make unit-test` | Library, Mac view model, agent, and tool tests (about 3 minutes) |
| `make test` | All of the above, plus iOS and UI tests (about 15 minutes) |
| `make check` | SwiftFormat, SwiftLint, behavior coverage, and personal data |

The code must build without warnings and pass SwiftLint with no findings.

Nothing personal goes into the repository. Team IDs, bundle IDs, and device names live in the git-ignored `local.mk`. The hooks in `.githooks/` (enabled by `make hooks`) refuse commits containing personal data, and the pre-push hook runs `make lint`. Don't bypass them.

## Commit messages

Every commit message follows this template. Older commits in the history predate it, so don't copy their style.

```
Short (50 chars or less) summary ("subject line")

More detailed explanatory text. Wrap it to 72 characters. The blank
line separating the summary from the body is critical (unless you omit
the body entirely). Use GitHub-flavored markdown, and make sure that
inline code specifically is enclosed in backticks.

Write your subject line in the imperative: "Fix bug" and not "Fixed
bug" or "Fixes bug." This convention matches up with commit messages
generated by commands like git merge and git revert. A properly formed
git commit subject line should always be able to complete the sentence
"If applied, this commit will <your subject line here>".

Further paragraphs come after blank lines.

- Bullet points are okay, too.
- Typically a hyphen or asterisk is used for the bullet, followed by a
  single space. Use a hanging indent.

You should reference any issue that is being addressed in the commit, as
e.g. "#1" for issue #1. If the commit closes an issue, state this on the
last line of the message (see below). This will automatically close the
issue on Github as soon as the commit is pushed there.

Closes #1
```
